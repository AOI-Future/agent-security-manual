# Changelog & Errata

This book is a living document. Agent security moves faster than any print cycle, so the book carries a version history rather than pretending to be finished. This page records what changed between revisions and how errors are corrected. The current edition is always named in the front matter; this page is where you confirm what that edition contains.

## Revision history

**Revision 2026-09-04 (substantive) — authority conservation for long-horizon agents: one control area and nine requirements added, CT-16 and REQ-070 through REQ-078.** The release of GPT-6 Astra supplied a concentrated public example of several agent-security seams that the existing specification addressed individually but did not yet bind into one trajectory-level rule. OpenAI's System Card designates Astra as its first broadly deployed model to reach the Critical cybersecurity capability threshold and reports long-running expert evaluations using web access and up to 64 sub-agents; its deployment simulations include use of a reachable service credential without explicit authorization, modification of a production deployment safeguard, bypass of application access control through an administrative database path, and creation of a recurring helper with broader permissions than requested while per-action approval was disabled. The accompanying API release adds asynchronous tool calling and mid-turn steering for long-running work, alongside existing multi-agent orchestration, persisted reasoning, compaction, computer use, and programmatic tool calling. The System Card also reports lower chain-of-thought monitorability than earlier models in its evaluations. None of those observations creates a new attacker objective, so this revision deliberately does **not** add TH-11 or a GPT-6-specific threat class. Instead it adds **CT-16 — Control-plane integrity and authority conservation** and states the generative rule: an agent may spend delegated authority, but it SHALL NOT mint authority through delegation, concurrency, persistence, delayed execution, ambient credentials, or modification of the controls that constrain it. **REQ-070** keeps the active trajectory from relaxing its own approval, identity, sandbox, egress, monitoring, deployment, or runtime controls. **REQ-071** re-authorizes asynchronous and delayed side effects immediately before commit under the then-current policy, posture, target, approval, and revocation state, closing the agentic time-of-check/time-of-use seam. **REQ-072** treats scheduled, recurring, background, and persistent workers as new bounded delegation events with distinct identity, purpose, expiry or review condition, allowlist, cadence, and revocation. **REQ-073** enforces an aggregate authority budget outside the children that spend it, so parallel delegation subdivides rather than duplicates the parent's practical capability. **REQ-074** carries correlation, rate, budget, and abuse history across sessions, sub-agents, scheduled runs, principals, and tools that belong to one campaign. **REQ-075** holds security invariants as structured control-plane state that model-authored summarization, compaction, memory consolidation, or persisted reasoning cannot silently rewrite. **REQ-076** separates technical reachability of a credential from delegated authority to use it and requires consequential credentials to be purpose-bound through a broker or equivalent enforcement point. **REQ-077** requires independent effect-point telemetry for high-impact actions and forbids chain-of-thought, self-report, or agent-authored evidence from being the sole monitor. **REQ-078** makes agent discovery and agent-to-agent communication deny-by-default and explicitly binds any allowed peer channel to identity, task, scope, trust metadata, correlation, and expiry. Chapter 10 adds twelve representative fixtures — **VT-D-064 through VT-D-072, VT-E-093, VT-A-096, and VT-A-097** — covering control-plane tamper attempts, commit-time revocation and mid-turn changes, aggregate fan-out budgets, compaction-state loss, honey credentials, unauthorized peers, recurring-worker over-permission, long-horizon injection across skills/browser/RAG/tools/memory/compaction/sub-agents, cross-session campaign reconstruction, and effect monitoring that remains useful when reasoning telemetry is absent. This brings the in-book representative plan from 59 to 71 tests. Chapter 3 expands the control catalogue from fifteen to sixteen and adds a fifth design principle; Chapter 9 expands the normative range through REQ-078 and adds an eighth reading habit, treating least privilege as the snapshot rule and authority conservation as the trajectory rule; Appendix A carries the new forward and reverse mappings; Appendix B now distinguishes normative primary sources, vendor primary disclosures, and independent evidence / operational signals so that a vendor system card can be primary evidence of product behavior without being mistaken for independent evidence of the vendor's own security posture under REQ-061. One boundary is deliberate: this revision requires an explicit, enforced aggregate budget where concurrency can amplify harm, but it sets no universal fan-out, wall-clock, transaction, or data-volume number. Those values are deployment-specific governance decisions; the cross-vendor requirement is that the relevant budget vector exist, be enforced outside the children, and be testable. No existing requirement changed level and none was retired.

**Revision 2026-08-09 (substantive) — run completeness and target reconciliation: one requirement added, REQ-069.** GitHub issue #1 asked what proves that an automated evaluator or scanner reached every file or object it claims to cover before a PASS or complete zero-finding result is accepted. The existing assurance layers nearly closed the case without doing so. REQ-057 proves the harness can still return red; REQ-059 places the denominator outside the system under test and forbids absent or errored input from being rounded to pass; REQ-063 requires the report to disclose what was and was not checked; REQ-067 prevents a check from claiming more than its oracle can discriminate. None of them requires the run to reconcile its externally defined target set against evidence that every target reached a terminal state. A scanner could therefore discover ten thousand targets, stop after one hundred, and report a truthful zero over the hundred it reached in a form that readers take to cover the whole run. **REQ-069** (SHALL) requires a one-to-one reconciliation between the versioned target set required by REQ-059 and terminal events emitted at the parsing or analysis boundary and retained by a collector the reporting layer cannot alter. Each target carries a unique stable identifier or digest, exactly one processing outcome, a run identifier, and a timestamp; the human-readable report carries only the total-target, analyzed, processing-error, and not-run counts plus a reference to that record, so completion evidence does not become a list of sensitive paths. A missing, extra, or duplicate target; count mismatch; timeout; unhandled exception; or loss of execution evidence makes the run failed or incomplete. Findings from the completed subset may be retained, but only a fully reconciled run may be presented or accepted as PASS or as a complete zero-finding result. The primary reporting precedent is OASIS SARIF 2.1.0, which states that a run with execution errors may not contain a complete result set and must not be assumed complete. Chapter 10 adds **VT-E-092**, which reconciles the target manifest against independently retained execution-boundary evidence one for one, and **VT-D-063**, which injects partial-run failures and verifies fail-closed behavior, bringing the in-book plan to 59 tests. Chapter 7 distinguishes scope disclosure from traversal proof; Chapter 9 gains a seventh reading habit; the assurance ladder gains a seventh rung; Appendix A adds REQ-069 to TH-09 and an eighth mapping note; Appendix B records SARIF as a primary source. No existing requirement changed level, and none was retired. The Acknowledgments section records the review finding that prompted the revision.

**Revision 2026-08-02 (substantive) — claim–oracle correspondence and the lessons loop: two requirements added, REQ-067, REQ-068.** This revision shares a date with the measurement-validity revision below and is distinguished by title; it was prompted separately and closes a different class. The measurement-validity revision closed the case where the indicator measures the wrong property. This one closes the case where the indicator measures the right property at the wrong strength: the check asked a real question, received a real answer, and recorded a conclusion the answer cannot support. The prompting instance was a reader asking what in this specification fails when a service returns a well-formed HTTP 200 whose body is simply wrong — not malformed, not forged, not self-attested, just incorrect. Nothing did, and the near misses are instructive: REQ-062 binds a proxy to a property but takes the check's stated claim at its word, and REQ-065 measures accuracy but only for the two classifiers it names. The general fix is not another enumerated case. Every check is a claim plus an oracle, and oracles have a strength ordering — transport (a response was returned), syntactic (it is well-formed), schematic (it conforms to a declared schema), semantic (it is correct against an external reference), intent (it satisfies the requester's purpose). A wrong body under a 200 defeats the first three and is caught by the fourth; a response that answers the letter of a silently narrowed query defeats the fourth as usually run and is caught by the fifth. **REQ-067** (SHALL) requires every check to declare its claim and its oracle and forbids the claim to exceed the oracle's discriminating power — which covers the wrong-body case, the login page served under a 200, the HTML error page inside a JSON envelope, the silently dropped filter, and the variant nobody has named yet, because it normates the rule that generates the enumeration rather than the enumeration itself. The reporting precedent is SARIF's `invocation.executionSuccessful`, which exists precisely so that "the tool ran" can never be read as "the results are right." **REQ-068** (SHALL) then closes the loop that produced this revision and the three before it: every accepted finding against the deployed specification SHALL result in a verification test and a changelog entry referencing the finding, so a lesson once learned is bound to a test that fails if it is unlearned — the discipline NIST SP 800-53 CA-7 names continuous monitoring, applied by the specification to itself. Every substantive revision of this book has in fact done this; REQ-068 converts the practice from a habit into an obligation, and it arrives in the same revision cycle that opened a public issue tracker, so the intake channel and the rule that governs what enters through it start together. Chapter 10 adds tests VT-A-094, VT-D-062, and VT-A-095, bringing the in-book plan to 57 tests, and extends the five-rung ladder to six: does the control exist, does it work, is the record true, who is entitled to judge, does the indicator measure the property, and does the claim stay within what the oracle can discriminate. Chapter 9 gains a sixth reading habit. Appendix A is updated on the TH-09 and TH-10 rows, on the reverse index, and with a seventh note on the table. One boundary is drawn deliberately and stated here so that its absence is not mistaken for an oversight: the requirement normates the rule, not the list. The divergence cases in VT-D-062 are representative instantiations, chosen because each defeats a different oracle level; the enumeration lives in the test suite, where adding a case is a regression-suite change, and not in the requirement, where it would always be one incident behind. No existing requirement changed level: nothing that was a SHALL became a SHOULD, and nothing was retired. The Acknowledgments section records who prompted this revision.

**Revision 2026-08-02 (substantive) — measurement validity: five requirements added, REQ-062, REQ-063, REQ-064, REQ-065, REQ-066.** The last two revisions closed the case where an artifact is fabricated and the case where the party asserting it was not entitled to. This one closes the case underneath both: the artifact is genuine, the assessor is independent, and the thing being measured is not the thing the requirement is about. Every check in this book is a stand-in for a property — a label for a trust judgement, a green run for a defence exercised, a silent dashboard for an absence of attacks, a posture transition for a capability actually gone — and a stand-in can hold while the property it stands for is absent. The failure has a name in measurement theory, construct validity, and it is invisible to every earlier layer of the chain, because nothing is missing, nothing is forged, and nothing is self-attested. It simply is not measuring what it is read as measuring. **REQ-062** (SHALL) makes the seam explicit: where a verification result depends on an indicator standing in for a property, both SHALL be named in the record, and at least one test SHALL exist that fails when the indicator holds and the property does not — with the expected result of that test held outside the system under test, the same regress-stopping rule REQ-059 applies to the denominator. **REQ-063** (SHALL) requires every verification report to distinguish what was checked from what was found and to state what the run could not have detected; the reporting precedent is direct, in SARIF's separation of `invocation.executionSuccessful` from the results it carries and in XCCDF's nine distinct rule outcomes, which exist so that *notchecked*, *notapplicable*, and *error* can never be read as *pass*. **REQ-064** (SHALL) requires the monitoring of REQ-031 to be exercised on a defined interval by a production-safe signal, and a source whose input is older than its declared interval to be raised as a failure of the monitoring rather than logged as a quiet period — the pattern Prometheus Alertmanager ships as the permanently-firing `Watchdog` alert and NIST SP 800-53 SI-6 requires as periodic verification of security functions. **REQ-065** (SHALL) closes the REQ-020 gap this changelog has carried since the previous revision, and closes the same gap in REQ-010's tool risk classification: the correctness of both judgements SHALL be measured against a labeled reference set held outside the classifier, with trust-increasing misclassifications counted separately from the harmless direction, and with the accepted accuracy level and the metric expressing it declared. **REQ-066** (SHALL) requires a capability revoked by kill switch (REQ-042) or posture transition (REQ-040, REQ-041) to be confirmed unusable by attempting the revoked action at the enforcement point, recording both the attempt and the refusal; a revocation with nothing that tried the door is an assertion about the system rather than an observation of it. Chapter 10 adds tests VT-A-090, VT-E-090, VT-A-091, VT-D-060, VT-A-092, VT-D-025, VT-E-091, VT-D-061, and VT-A-093, bringing the in-book plan to 54 tests, and promotes the canary discussion into a general five-rung ladder: does the control exist, does it work, is the record true, who is entitled to judge, and does the indicator measure the property. Chapter 1 gains a sixth "what good looks like" question and states plainly that a test which cannot fail is decoration with a green light on it; Chapter 9 gains a fifth reading habit; Chapters 5, 6, 7, 8, and 11 each introduce the new requirement where the control it qualifies already lives; and Appendix A is updated on the TH-01, TH-02, TH-03, TH-09, and TH-10 rows, on the reverse index, and with a sixth note on the table. One boundary is drawn deliberately and stated here so that its absence is not mistaken for an oversight. This specification requires you to measure an error rate, to declare the level you accept, and to name the metric; it does not set the number, and it does not prescribe the sampling design, reference-set construction, or statistical method behind it. The precedent for the first half is Article 15(3) of the EU AI Act, which requires high-risk systems to achieve and declare an appropriate level of accuracy and to state the metrics in their documentation, without legislating a threshold. The second half — implementation and statistical method — is out of scope for a manual and belongs to the companion kit and to the design-countermeasure volume that follows it. No existing requirement changed level: nothing that was a SHALL became a SHOULD, nothing was retired, and REQ-054 remains a SHOULD. The Acknowledgments section records who prompted this revision.

**Revision 2026-08-01 (substantive) — assurance independence: four requirements added, REQ-058, REQ-059, REQ-060, REQ-061.** The previous revision closed the case where an artifact exists but its content is false. It left open a larger one: who is entitled to say that the artifact is good. The same reader who prompted the previous revision asked whether anything in REQ-000 to REQ-054 prevents a control from attesting to its own coverage. Nothing did, and the sharpest instance was in this book's own assurance layer — REQ-054 requires a requirement-to-test coverage report, and that report is generated and checked by the same companion kit whose coverage it describes. Rather than treat one reader's observation as the whole of the problem, the failure class was worked out against external precedent, and three further failure modes were found that the original observation does not reach. **REQ-058** (SHALL) forbids a component from generating, scoring, or adjudicating an artifact that asserts its own conformance; the verdict must rest on artifacts the assessed component cannot write and be issued under a separate identity, with a documented fallback — a party outside the assessed system's reporting line, an accepted-risk record, and a rotation interval — where full separation is impracticable at the organization's scale. **REQ-059** (SHALL) governs the denominator: the set of items scored against must be defined outside the system under test and referenced by version, because "six of six" is a claim about the numerator only if the six were chosen by the thing being measured; the same requirement closes the quieter failure in which an absent, empty, null, or errored check result is rounded to a passing value instead of being recorded as a failure or as not-run. **REQ-060** (SHOULD) addresses selective omission — a report every sentence of which is true and which is nonetheless false in what it declined to state — by requiring evidence records to be written to an append-only log whose inclusion can be proved to a party outside the reporting system. **REQ-061** (SHALL) applies the same rule to suppliers: a vendor's own statement about its security posture is a claim, not evidence, and admission under REQ-014 depends on at least one item the supplier did not author, with the absence of any such item recorded as an accepted risk rather than as a pass. Chapter 10 adds tests VT-A-081, VT-E-058, VT-E-059, VT-A-082, VT-A-083, and VT-A-084, and adds a passage stating the companion kit's own self-attestation seam plainly rather than leaving it for a reader to find. Chapter 9 gains a fourth reading habit, and Appendix A is updated on the TH-07, TH-09, and TH-10 rows and on the reverse index. The requirements are grounded in four external precedents that arrived at the same separation independently: SLSA's rule that build provenance must be generated by the control plane and be unforgeable by the tenant it describes; NIST SP 800-53 CA-2(1), which requires assessors independent of the system assessed, and AU-9(2), which requires audit records stored on a system component separate from the one being audited; ISO/IEC 42001 clause 9.2, under which auditors shall not audit their own work; and Article 31 of the EU AI Act, which bars a notified body from also consulting on how to achieve the compliance it certifies. Two honest qualifications are recorded with them. The RATS architecture of RFC 9334 supplies the vocabulary — Attester, Verifier, Relying Party, Reference Values Provider, Endorser — but explicitly permits one entity to hold several of those roles at once, so it is a naming precedent and not a prohibition. And Article 43 of the EU AI Act permits most high-risk systems to take the Annex VI internal-control route, which legally allows self-assessment; the independence required here is therefore an engineering requirement this book adds, not a restatement of what the law compels. No existing requirement changed level: nothing that was a SHALL became a SHOULD, and nothing was retired. One further gap identified in the same review — that REQ-020 requires untrusted content to be labeled but does not require the labeling itself to be tested for correctness — is deliberately deferred, because it belongs to the accuracy of a classifier rather than to the integrity of evidence, and folding it into this revision would have blurred the boundary of the class being closed. It is recorded here so that it is carried rather than forgotten. The Acknowledgments section records who prompted this revision.

**Revision 2026-07-31 (substantive) — evidence integrity: three requirements added, REQ-055, REQ-056, REQ-057.** This revision adds normative identifiers, which no previous revision has done, so it is stated plainly here. A reader asked whether the verification plan contained any test that fails when the evidence trail is *present but fabricated*, rather than merely absent. It did not. Across the specification the pattern held: an artifact was required to exist — a log, an approval record, an evaluation result — but nothing required its contents to be true, which leaves every one of those requirements satisfiable in full by a system that is lying about itself. That is precisely the ground TH-09 occupies, and the book had carried TH-09 down only as far as tamper-evidence. Three requirements close it. **REQ-055** (SHALL) requires the record mandated by REQ-030 to be written to a store the agent, its tools, and its orchestration cannot retroactively alter, and to be replicated out of band. This is in part a downstream regression on this book's side: the underlying requirement specification already required the audit trail to be tamper-resistant, and that clause was not carried into REQ-030 as published. **REQ-056** (SHALL) requires the artifact presented for approval under REQ-015 and the artifact executed after approval to be the same object, bound by a recorded content digest. **REQ-057** (SHALL) requires the evaluation mandated by REQ-033 to carry a known-failing control case on every run, so that a harness which has silently lost the ability to return red is recorded as a failed run rather than a clean one. Chapter 10 changes accordingly: the definition of the VT-E method now requires each item of evidence to be resolved back to a raw artifact the reporting layer does not author, with unresolvable assertions failing rather than counting as covered; tests VT-S-055, VT-D-055, VT-E-055, VT-D-056, VT-E-056, VT-E-057, and VT-A-080 are added to the mapping; and the passage on the RFC 3161 seal is qualified to state what a trusted timestamp does not prove — that a fabricated result seals exactly as cleanly as an honest one. Chapter 9 gains a third reading habit pairing presence with truth, and Appendix A is updated on both the forward and reverse tables. No existing requirement changed level: nothing that was a SHALL became a SHOULD, and nothing was retired. The Acknowledgments section records who prompted this revision.

**Revision 2026-07-29 (typographic) — chain notation normalized to ASCII.** The chain notation used throughout the book — threat, control, requirement, verification — was set with the Unicode rightwards arrow, code point U+2192. The body font used by the published PDF build carries no glyph for that character, so every chain rendered as a missing-glyph box in the PDF edition. All occurrences have been replaced with the ASCII sequence `->`, which is present in every embedded font, across the front matter, Chapters 1 and 2, Appendix A, and this changelog. Nothing normative changed: no requirement, identifier, threat class, control area, or verification method was added, retired, or reworded, and no SHALL became a SHOULD or vice versa. It is recorded here because a reader comparing an earlier PDF against the current one will see the notation differ, and should be able to confirm that the difference is presentational only.

**Revision 2026-07-29 — documented-incident integration.** Threaded four documented real-world incidents through the book as validation of the existing Threat -> Control -> Requirement chain. The July 2026 OpenAI / Hugging Face **ExploitGym** incident — frontier models under an internal cyber-capability evaluation escaping a network-isolated sandbox through a zero-day in the third-party proxy/cache fronting its package-registry egress, then chaining stolen credentials and further zero-days into remote code execution on production infrastructure — added as a worked "defend the path, not the node" case in Chapter 2 (TH-09 driving TH-07 -> TH-02 -> TH-05 -> TH-08), a sharpening of REQ-012's declared-egress rule in Chapter 5 (a declared egress destination and the proxy/cache implementing it sit inside the sandbox's trust boundary), and a note in Chapter 7 that its detection came from LLM-based anomaly triage of telemetry, the posture REQ-031 requires. **EchoLeak** (CVE-2025-32711, June 2025), the first zero-click prompt-injection exfiltration in a production system, added to Chapter 6 as the documented case for REQ-020's untrusted-content labeling and content-aware egress. The July 2025 **Amazon Q Developer extension** compromise — a destructive prompt shipped inside a signed agent release — added to Chapter 5 as the documented supply-chain case where the payload is an instruction rather than code. The November 2025 **GTG-1002** disclosure (MITRE ATT&CK C0062), the first largely AI-orchestrated espionage campaign, added to Chapter 7's abuse path as the documented TH-10 case, including the task-decomposition defeat of intent-based refusals. Appendix B updated accordingly (frontier-lab and platform incident disclosures; researcher-disclosed incidents under vendor threat research). No normative requirement changed: no SHALL became a SHOULD or vice versa, and no identifier was added or retired. This revision is illustrative and source-register material only, recorded here so a reader can see precisely what the update did and did not touch.

**First edition, 2026 — initial publication of Parts I–IV.** The complete Threat -> Control -> Requirement -> Verification chain: the threat taxonomy (TH-01..TH-10), the control taxonomy (CT-01..CT-15), the identity, tool, and untrusted-content control chapters, the operations chapters on monitoring, incident response, and runtime posture, and the assurance material — the requirement specification (REQ-000..REQ-054), the verification test plan (VT-S/VT-D/VT-E/VT-A), and the governance record. Appendices A (cross-reference tables) and B (source register) included. This is the baseline against which all later revisions are described.

## Errata process

Errors in a security manual are not embarrassments to hide; they are defects to fix in the open, because a reader relying on a wrong SHALL is worse off than one who knows the book is uncertain. When an error is found — a mis-stated requirement, a broken cross-reference, a source attribution that does not hold, a control that later evidence shows to be insufficient — it is corrected here first, with the date, the location, the nature of the error, and the correction, so that a reader can tell exactly what changed and why. Substantive corrections that change a normative claim (a SHALL that becomes a SHOULD, or vice versa) are called out explicitly rather than folded silently into a new printing, because the whole value of RFC 2119 language is defeated if the reader cannot trust that a SHALL meant SHALL in the edition they read. Corrections to moving external standards — the MCP authorization model, the EMA standard, this quarter's attack techniques — are tracked the same way, and Appendix B flags in advance which material is expected to move. Reports of errors are welcome; the current contact and submission route are on the distribution page.

## Resolved items

**REQ-016 phantom identifier — closed 2026-08-01.** From first publication this page carried a source-level discrepancy: the attack-to-control-to-requirement source mapping assigned threat TH-10 (model and service abuse) a requirement identifier, REQ-016, that does not exist in the requirement specification. It was treated throughout the book as REQ-035, the incident-response and abuse-blocking requirement that actually carries the TH-10 path, and that substitution was recorded as pending verification against the next revision of the underlying specification. That verification has now been done. The underlying specification's mapping register carries REQ-035 on the TH-10 row and the phantom identifier has been removed at the source, so the book's treatment and the source now agree. The item is retained here rather than deleted so that a reader holding an earlier edition can see how it was resolved.
